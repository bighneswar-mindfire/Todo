## Problem

A user can delete a note, but the app has no way to see or restore it. The backend already serves `GET /notes/trash` and `POST /notes/{id}/restore`, and the SDS routes list `/trash`, yet the frontend has no trash page and no Restore action. A deleted note is unrecoverable from the UI inside its 30-day window.

## Scope

- `/trash` page behind `ProtectedRoute`, linked from the notes list.
- List trashed notes newest deletion first, paginated, with loading, empty and error states.
- Restore button per note: calls `POST /notes/{id}/restore`, removes the row, and refreshes the notes list so the note reappears with its tags.
- Failure handling: 404 (not deleted or outside 30 days) shows an error and refetches the list; other errors keep the row and show an alert.
- API functions and query hooks use `@todo/shared` types and schemas; all HTTP goes through `api/client.ts`; page state lives in the URL.

## Out of scope

Backend, database or `packages/shared` schema changes; permanent delete or "empty trash"; opening, previewing or editing a trashed note; restore from the editor; bulk restore; the Playwright journey (AB-1016).

## Acceptance (drafts for the spec, each to become one named test)

- WHEN the user opens `/trash` with trashed notes THEN they are listed newest deletion first.
- WHEN there are none THEN an empty state is shown.
- WHEN the user presses Restore THEN `POST /notes/{id}/restore` is sent, the row disappears and the note is back in the notes list with its tags.
- WHEN the server returns 404 on restore THEN an error shows and the list refetches.
- WHEN the request fails with another error THEN the row stays and an alert shows.
- WHEN the trash list request fails THEN an error state with retry is shown.
- WHEN the user is signed out THEN `/trash` redirects to `/login`.
